# Project onboarding

## Procedure

1. **Preview the deterministic setup.** From the repository root, run [onboard.py](./scripts/onboard.py) with its absolute path (resolve it from this file's folder): `python <path>/onboard.py --repo . --dry-run` (`python3` on Linux and macOS), plus `--docs` when the user wants the architecture map. It prints a JSON summary: the Azure DevOps coordinates parsed from `origin`, the base branch, the planned `.vscode/mcp.json` change and the `.git/info/exclude` entries. It never prints credentials.
2. **Review the summary with the user**, then run the script again without `--dry-run`. Options: `--base-branch <name>` overrides the detected base branch; `--force` replaces conflicting `ado-read` or `ado-write` definitions; `--docs` creates the architecture map skeleton in `docs/architecture/`, or in `--docs-path <folder>` when the project keeps its documentation elsewhere (existing files are never overwritten). When the action is `manual` (the existing `mcp.json` has comments or cannot be parsed), show the printed snippet and let the user merge it. Exit code 3 (`ok: false`, `conflicts`) means `ado-read` or `ado-write` already exist with another definition: show both to the user and rerun with `--force` only if they agree. On a .NET project (`*.sln`, `*.slnx`, `*.csproj`, `*.fsproj`, `*.vbproj` or `global.json`, or `--dotnet`), the script also adds the read-only `ms-learn` documentation server (Microsoft Learn MCP, no sign-in); the `dotnet-performance` skill uses it. An Azure DevOps Server (on-premises) remote is reported in `azure_devops_server` with a warning: no MCP configuration is generated, so work item intake and draft PR creation stay manual.
3. **Gather the project facts** (read-only): build, lint and test commands (README, package manifests, `Makefile`, `azure-pipelines.yml`, CI scripts), code conventions, where the domain knowledge lives (glossary, docs, wiki), and the existing skills (`.github/skills`, `.agents/skills`, `.claude/skills`) and instructions.
4. **Map the application (recommended).** Ask the user whether to map it now. If yes, follow the initial mapping procedure of the `architecture-mapping` skill: it fills the skeleton created by `--docs`, shows the pages and the "To confirm" items to the user, and commits them on a dedicated branch for a PR. The architect starts every design from this map, and every workflow PR keeps it up to date. If the project already documents its architecture, point the contract to that folder instead.
5. **Write the project contract.** Fill the [AGENTS.md section template](./assets/agents-md-section.md) and add it to `AGENTS.md`, creating the file if needed. `AGENTS.md` is usually tracked by git: show the change and ask before writing it.
6. **Commit the onboarding.** Commit `AGENTS.md`, and `.vscode/mcp.json` when it is tracked, on the base branch (for example `docs: add the AI delivery workflow contract`) or through the team's usual PR. The workflow starts from a clean working tree: uncommitted files would be carried onto the work branch and trip the review gate.
7. **Check the environment** and report what is missing:
   - VS Code settings: `chat.plugins.enabled`, `chat.pluginLocations` (path of this plugin), `chat.useHooks`; the workspace must be trusted.
   - Python on the PATH as `python` (Windows) or `python3` (Linux, macOS), for the hooks.
   - MCP: start `ado-read` and `ado-write` from the MCP servers view (Microsoft Entra sign-in), then list the project's repositories with an `ado-read` tool.
